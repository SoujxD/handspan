Handspan · computer-use automation for back-office banking

Architecture

An LLM works out how to do a task in a UI that has no API — once. That run is compiled into a typed capability. The capability then replays with no model in the loop, thousands of times.

01

The whole system, one picture

Two halves that never run at the same time, joined by a file. Everything the automation does — in either half — reaches the application through the same adapter, and passes the same gate on the way.

the model is involved; this costs money deterministic; zero model calls
02

The flow, stage by stage

Follow the picture left to right, then top to bottom. Each stage below says what goes in and what comes out.

Stage 1
discovery

A model drives the real application

You hand it a goal in English. It opens a browser and works the screens — but it never sees HTML. It sees the page the way a screen reader does: a list of controls with a role, a visible label, and which panel and frame each one sits in. It points at things by a throwaway handle like e17, reissued every time the screen is looked at.

Because the tool it is given has no selector parameter, it cannot write one down even if it wanted to. Constraining the tools is what constrains the artifact.

in goal + entry URLout a trace of every action, with before/after screen statecost ~11–22 model calls, once
Stage 2
compile

Code turns the run into a contract

The model proposes; the compiler disposes. It rewrites each target as a plain description, invents a checkpoint for any step that changed something and lacks one, re-derives how risky each action is from policy rather than trusting the model, and throws away any literal that was bound to a parameter — passwords unconditionally.

Then the schema checks its own rules. If anything is unsafe, the recording fails loudly instead of producing a plausible artifact that misbehaves in three weeks.

in the traceout a capability, marked draft
Stage 3
the artifact

One JSON file, reviewed like code

This is the pivot of the whole system, and the thing to open on screen. It holds the typed inputs a caller supplies, the typed outputs it gets back, the ordered steps, the declared unhappy paths, the per-institution bindings, the risk policy, and who approved it.

A calling agent can read the inputs, outputs and outcomes and know exactly what it needs and what can happen — without reading a single step.

lives in gitversions immutable and additiveruns when a human approves it
Stage 4
replay

The same flow, without the model

An agent calls the capability by name with typed arguments. The engine walks the recorded steps against the live application. Nothing here reasons: it looks up each control by description, acts, and verifies. No model client is even constructed, and the result carries a count of model calls that is asserted to be zero before it is returned.

in capability + inputs + which institutionout one of four result shapescost a browser, no tokens
Stage 5
the answer

Four shapes, so they cannot be confused

Success and a business outcome are different things but both are fine — "no such member" is an answer, not a crash, and both exit zero. An escalation means a person now holds the browser. A failure carries the step, what was expected, what was actually on screen, and a screenshot.

They are separate shapes rather than values of a status field, so a caller physically cannot read outputs off an outcome — the field is not there.

HTTP success 200 · outcome 200 · escalated 202 · failure 4xx/5xx
03

Inside one replay step

The order is fixed, and the order is the error handling. Guards run before every step — not only where a problem was first seen — which is how a surprise screen is caught wherever it appears.

04

Handing control to a human

When the system cannot safely continue, a person takes over the same live browser window — same cookies, same half-filled form. Not a fresh session.

05

After day one: drift and repair

A capability is not a program — it is a description of a screen, and screens change. When the vendor renames a field, nothing errors anywhere; the recording just quietly stops matching. Finding that is the part that does not scale at thousands of app instances.

Worth saying out loud

Ordinary renames are worked out with no model at all — the saved proposal reports Model calls: 0. A model is spent only on a genuinely ambiguous case, and even then it may only pick a label that was actually on screen. Same principle as the system itself: spend the model where judgement is needed, and nowhere else.

Every component, in one line

ComponentWhat it doesWhy it exists
agent/loop.tsDrives the browser with the model: observe, decide, act, record.A policy denial must come back as something the model can reason about, not an exception.
agent/tools.tsThe only actions the model may take.No selector parameter exists, so a selector can never enter the artifact.

web/resolver.tsFinds the control a description refers to.Scores several weak signals, and refuses when two candidates tie.
web/playwright-surface.tsMoves the mouse, types keys, reads frames.A driver only — Playwright's own matching is never used, so the flow stays portable.
replay/engine.tsExecutes a capability against the live app.The production path. No model is imported below this line.
replay/evaluate.tsAnswers "is this condition true?" and pulls values off the screen.Checkpoints mean the same thing at record time and replay time.
replay/drift.tsReports how far the screen has moved from the recording.Detection is what does not scale; the signal was already in every run.
repair/propose.tsWrites a proposed new version for drift that is safely fixable.Repair is a reviewed change to a file, never an edit and never a live decision.
safety/policy.tsDecides whether an action may happen at all.One gate, below both halves, on the only path to the browser.
safety/redaction.tsKeeps credentials and regulated data out of anything written down.Exact values for declared secrets; patterns as a backstop.
control/lease.tsTracks who is holding the browser session.Enforced at the surface, so automation physically cannot act while a person holds it.
control/escalation.tsDecides when a human is needed and packages the context.Detection, routing and transfer are three different jobs.
operator/server.tsThe console a person takes control from.The handoff is real; the video feed is deliberately a screenshot poll.
catalog/store.tsLoads and saves capabilities; projects them as agent tools.An unpinned load takes the newest approved version, never the newest.
catalog/server.tsTwo HTTP endpoints: list capabilities, invoke one.Because the artifact is already a contract, this needed almost no code.
evidence/recorder.tsWrites the log, screenshots and snapshots for every run.The redactor is a constructor dependency, so unredacted writing is unreachable.
